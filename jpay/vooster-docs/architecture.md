# **제품 요구사항 문서 (PRD) – PairPay (MVP)**

## 1. 요약 (Summary)

PairPay는 2인 관계(커플, 친구, 룸메이트)의 공동 지출을 가장 쉽고 빠르게 관리할 수 있도록 설계된 **PWA(Progressive Web App)**입니다. 복잡한 로그인 절차 없이 초대 코드로 즉시 연결되며, **Supabase를 백엔드로 활용**하여 실시간 데이터 동기화를 지원합니다. MVP의 핵심 목표는 **‘공동 지출 기록 → 현황 파악 → 예산 관리 → 정산’**의 핵심 사이클을 완벽하게 구현하여 사용자에게 즉각적인 가치를 제공하는 것입니다.

## 2. 문제 정의 (Problem Definition)

1.  공동 지출을 엑셀이나 메모장으로 관리하는 것은 번거롭고, 오류가 발생하기 쉽다.
2.  기존 가계부 앱은 개인용이라 공동 지출만 분리해서 관리하기 복잡하다.
3.  "누가 얼마를 더 썼는지" 계산하고 정산하는 과정에서 감정적인 부담을 느낀다.
4.  공동의 예산을 설정하고 함께 지키려는 노력을 체계적으로 관리할 도구가 없다.

## 3. 목표 및 핵심 지표 (Goals & Key Metrics)

### **제품 목표**
- **1차 목표:** 공동 지출 기록 및 정산 과정을 획기적으로 간소화하여 관리 부담을 없앤다.
- **2차 목표:** 공동 예산 설정 기능을 통해 사용자들이 합리적인 소비 습관을 형성하도록 돕는다.

### **핵심 지표 (MVP 출시 후 3개월 기준)**
- **온보딩 완료율:** 초대 코드 입력 후 첫 지출 기록까지의 전환율 ≥ **80%**
- **주간 활성 페어 (WAP):** 한 주에 한 번 이상 앱을 실행한 페어 수 ≥ **1,000**
- **핵심 기능 사용률:** 활성 페어 중 '공동 예산' 기능을 설정한 페어 비율 ≥ **30%**
- **NPS (순수 고객 추천 지수):** ≥ **40**

## 4. 대상 사용자 (Target User)

- **주요 사용자:** 명확한 목적(데이트 비용, 생활비, 여행 경비)을 가지고 정기적으로 돈을 함께 쓰는 20~30대 2인 관계
- **Pain Points:** 돈 계산의 번거로움, 정산 시 어색함, 과소비에 대한 막연한 불안감
- **Needs:** 누가 얼마를 썼는지 실시간으로 투명하게 확인하고, 간편하게 정산하고, 함께 세운 예산을 잘 지키고 싶다.

## 5. MVP 기능 요구사항 (In-Scope)

### **F-1. (보류) 페어 연결 (Pair Connection)**
- **설명:** 해당 기능은 후순위로 두고, MVP에는 모든 사용자가 로그인 또는 초대 없이 접근 가능하도록 공개형 접근 방식을 우선 적용함. 페어 연결 및 초대코드 기능은 추후 확장 시 구현 예정.
### **F-2. 지출 기록 (Expense Logging)**
- **기능:**
    - 지출 금액, 날짜, 카테고리, 결제자, 간단한 메모를 입력하는 기능
    - 분담 비율 설정 (5:5 기본, 수동 비율, 100:0)
    - **(선택) 영수증 사진 첨부 기능 (1장)**
- **세부 요구사항:**
    - 카테고리는 '식비', '교통', '생활', '문화', '기타' 등 기본 5개 제공
- **AC:** 사용자가 4번의 탭/클릭 이내에 지출 기록을 완료할 수 있어야 한다.

### **F-3. 실시간 대시보드 (Dashboard)**
- **기능:**
    - **'주고받을 금액'**을 실시간으로 표시 (예: "A가 B에게 15,000원")
    - 이번 달 공동 총지출액 표시
    - **카테고리별 지출 비중**을 보여주는 원형 차트
- **세부 요구사항:**
    - 차트는 `shadcn/charts` (recharts 기반)를 활용하여 구현
- **AC:** 새로운 지출이 기록되면 대시보드의 모든 수치는 2초 내에 갱신되어야 한다.

### **F-4. 공동 예산 설정 (Shared Budget)**
- **기능:**
    - 페어 단위로 **월별 총예산**을 설정하는 기능
    - 예산 대비 현재까지의 지출 현황을 보여주는 게이지 바(Gauge Bar) 표시
- **세부 요구사항:**
    - 예산 설정은 선택 사항이며, 미설정 시 해당 UI는 노출되지 않음
- **AC:** 예산 금액을 입력하고 저장하면 즉시 대시보드에 게이지 바가 반영되어야 한다.

### **F-5. 정산 및 내역 관리 (Settlement & History)**
- **기능:**
    - 전체 지출 내역을 최신순으로 보여주는 리스트
    - **'정산하기'** 버튼을 누르면 "총 OOO원을 정산하시겠습니까?" 확인 팝업 노출
    - 확인 시, '주고받을 금액'은 0으로 리셋되고, 이전 내역은 '지난 기록'으로 상태 변경
- **세부 요구사항:**
    - '지난 기록'은 조회만 가능하고 수정/삭제는 불가
- **AC:** '정산하기' 완료 후 대시보드의 잔액이 즉시 0으로 변경되어야 한다.

## 6. 제외되는 기능 (Out of Scope for MVP)

- **페어 연결/초대코드 기능:** MVP 이후 구현 예정. 초기 버전은 모든 사용자가 제한 없이 접근 가능함.
- **공동 저축 목표 기능:** MVP 이후 가장 먼저 고려할 기능
- **주기성/반복 지출 등록:** 월세 등 고정비 자동 등록 기능
- **항목별 분할 정산 (Itemized Splitting):** 영수증 내 개별 아이템 분담 기능
- **상세 리포트 및 데이터 내보내기(CSV):** 전월 대비 분석 등 고도화된 리포트
- **다중 통화 지원:** 해외여행을 위한 기능
- **푸시 알림:** 예산 초과, 수정 알림 등
## 7. 기술 고려사항 (Technical Stack)

- **프론트엔드:** **React (Vite 기반), TypeScript**
- **UI:** **shadcn/ui** (컴포넌트 라이브러리), **Tailwind CSS**
- **상태 관리:** **Zustand** (가볍고 간단한 상태 관리) 또는 **React Query** (서버 상태 관리)
- **백엔드/DB:** **Supabase**
    - **Database (Postgres):** `pairs`, `expenses`, `budgets` 테이블 관리
    - **Auth:** 로그인 기능은 없지만, 익명 사용자 세션을 `localStorage`와 연동하여 사용자 식별
    - **Storage:** 영수증 이미지 업로드 및 관리
    - **Realtime:** 지출 내역 실시간 동기화에 활용
- **배포:** **Docker** 기반 컨테이너 배포 (별도의 클라우드 플랫폼 지정 없음, 필요 시 추가 요청 예정)

## 8. 데이터 모델 (초안)

- **`pairs`**
    - `id` (uuid, pk)
    - `created_at` (timestamp)
    - `invite_code` (varchar)
    - `user1_name` (varchar)
    - `user2_name` (varchar)
- **`expenses`**
    - `id` (uuid, pk)
    - `pair_id` (fk to pairs.id)
    - `amount` (integer)
    - `description` (text, nullable)
    - `payer_name` (varchar)
    - `category` (varchar)
    - `expense_date` (date)
    - `image_url` (varchar, nullable)
    - `is_settled` (boolean, default: false)
- **`budgets`**
    - `id` (uuid, pk)
    - `pair_id` (fk to pairs.id)
    - `amount` (integer)
    - `month_year` (varchar, e.g., "2023-11")

## 9. 위험 및 대응 (Risks & Mitigation)

- **위험 1: Scope Creep (기능 범위 확장)**
    - **대응:** 본 PRD의 'Out of Scope' 섹션을 명확히 하고, 팀원 모두가 MVP의 핵심 가치에 동의한다. 모든 추가 기능 제안은 MVP 출시 이후 백로그에서 논의한다.
- **위험 2: 낮은 사용자 잔존율 (재방문율 저하)**
    - **대응:** MVP의 핵심 사이클(기록-확인-정산)이 얼마나 쉽고 빠른지에 집중한다. 사용자가 "이거 정말 편하다"라고 느낄 수 있도록 UX 완성도를 최대한 높인다.
- **위험 3: Supabase 기술 의존성**
    - **대응:** MVP 단계에서는 Supabase의 안정성을 신뢰하고 빠르게 개발한다. 장애 발생은 수용 가능한 위험으로 간주하며, 서비스 성장 시 백업 및 다중화 전략을 고려한다.
